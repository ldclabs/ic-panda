# Client contract for channels and shared legacy history

English | [简体中文](channel_migration_zh.md)

Version: 2026-10-18. This document describes the public client and interoperability contract; it does not establish completed production deployment.

## Formal channels

Cloud commands and HTTP PoP use `dmsg-cloud/1`. Starting from the genesis hash, the client verifies each control sequence, previous head, role rule, device signature and retained IC account proof. Invitations bind the target account and known head. An owner transfer requires both parties to approve the same request context; an expired target signature cannot be replaced automatically.

Joining does not rotate the epoch. While the channel is writable, an invitation control carries `envelope_upload`: the inviter wraps the current epoch key for the invitee's then-valid devices with content access, using the history-grant format (`dmsg-channel-history/1`, scoped to the current epoch only). The upload binds the current epoch and head; the relay retains the invitee's certified evidence as the control's `acceptance_evidence`. An invitation can be accepted only in the epoch in which it was issued. A key-bearing invitation also requires the invitee's security version to remain unchanged at acceptance, otherwise a new invitation is needed. After acceptance, `joined_epoch` is the current epoch, the channel remains writable, and the new member can read messages already sent in that epoch; older epochs still require history grants. If rotation is pending and the inviter can coordinate it, rotation completes first and the invitation includes the new epoch's key. Otherwise the invitation has no key: acceptance requires rotation and gives access from the next epoch, but if rotation completes before acceptance, the invitation expires.

Rotation is required when a member leaves or is removed, a `rekey` control is submitted, or a member's device holding the current epoch is revoked or loses content access. Owners, administrators and authorized members can submit rekey at any time; for example, rotate before inviting someone who should not read earlier messages in the current epoch. Merely adding a device updates the member's security version without rotation; the new device receives existing epoch keys through the account-synced channel record. Owners, administrators and `can_rotate` members already holding the current epoch can coordinate rotation. When unlocked, an authorized daemon automatically acquires a lease and completes pending rotation. Control commits, epoch activation and rotation requirements emit a `channel` hint through members' account hint channels (`event: "control"`, with channel ID; see connect-v1 7.5); message commits emit `event: "message"`. There is no per-channel WebSocket. Owners and administrators may revoke unaccepted invitations using `revoke_invite`. Invitations can be delivered as `dmsg://channel/join#<base64url(invitation JSON)>`; opening a link only prefills the join dialog.

A rotation lease binds the epoch, head, fencing value and digest of the complete recipient set. Recipients are `device:<account>:<device>`, limited to 500 currently valid devices with content access. Recovered devices rejoin after account-root rotation; there is no recovery recipient entry. HPKE plaintext is the random epoch key; info/AAD uses `dmsg/channel-epoch-envelope/1` and binds the scope above. Each rotation retains public recipient-set evidence; recipients verify their envelope and key confirmation before saving the key. Ordinary messages, files, controls and grants add no per-item ICP update.

Messages use independent random IDs and derive a message key from the epoch key with `dmsg/channel-message-key/1`; retries retain the ciphertext, ID and approval. If the relay did not store a message and the epoch or control head changed, it is re-encrypted under the current epoch with the same ID (C06). The encrypted body is `{text, file?, reply_to?, edit_of?, retract?, agent?, packet?}`. `reply_to`, `edit_of` and `retract` identify a message by `{seq, digest}`, where `digest` is the signed command's SHA-256. Edits and retractions apply only to the same author's messages. Retraction removes the original text and attachment reference on member devices but cannot recall copies already obtained. `agent` identifies the Agent ID and name that wrote through this device, an account claim signed with the body; `packet` carries a transfer package. Proposing a billing transfer pauses channel writes, so the desktop sends only ownership-transfer packages in the channel and delivers billing-transfer packages separately. Undecryptable or undecodable bodies and messages with missing epoch keys are marked unreadable while the cursor advances; they can be opened when that epoch is reread after obtaining its key. Members may report monotonic delivered/read cursors (`POST /v1/channels/:id/cursor`, `dmsg/channel/cursor/v1 {delivered, read|null}`); read status is sent only by user choice. `GET /v1/channels/:id/cursors` returns current members' cursors. Use the service's `next_seq`; sequences without history permission appear separately in `skipped`, so response count cannot determine completion. History grants independently select epoch ranges and wrap only for the target's then-valid device/recovery entries; on its next read, the recipient opens granted epochs and rereads only previously skipped messages. During billing transfer, the relay pauses ordinary writes; the owner can cancel through `billing/cancel`, and channel views expose `billing_transition`. Files retain fixed versions, original chunk authentication and complete SHA-256.

Certified records retain historical device evidence; current permission is not proof of past authority. Relay acceptance time is not an independent TSA timestamp. Previously obtained history keys cannot be remotely recalled; revocation isolation depends on a new root/epoch and is bounded by certification freshness.

## Personal legacy history

Product scope changed on 2026-10-22: official shared legacy-channel inheritance, administrator approval, member claims and history-grant handoff were removed from the public client, CLI and legacy website. Personal-history import, reading, per-channel deletion and synchronization remain available; see [legacy archives](legacy_archive.md). Previously created inactive inheritance drafts have a separate deletion entry point; no new drafts are created.

## Recovery and frozen-source comparison

Local encrypted storage retains formal-channel evidence, historical keys, migration objects, financial jobs and cached attachments. There is no recovery package; a new device obtains content through cloud sync after on-chain approval and root rotation. Personal archives are described in [legacy_archive.md](legacy_archive.md).

Final source comparison uses message/authority ingress proofs and frozen OSS file manifests. OSS proofs retain only the SHA-256 of the original Candid arguments, not bearer tokens; request IDs are still checked with the IC representation-independent hash. Message, channel-DEK and attachment changes are listed individually. A pre-migration snapshot must not be presented as completed production cutover.
