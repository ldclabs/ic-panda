# dmsg-login/1: Internet Identity login relay for local clients

English | [简体中文](login-v1_zh.md)

Drafted and implemented in desktop work package W1 on 2026-10-12. The login page is `/_/login` in `src/dmsg_frontend`; the client side is `dmsg daemon`, using `src/dmsg_client`'s `login` module and the callback in `src/dmsg_cli`. Revised on 2026-10-14 for actual Internet Identity behavior: II's `icrc34_delegation` does not support `targets` and issues unrestricted delegations. Requests therefore omit targets; the daemon uses the session private key to append a target-restricted delegation (section 4). Desktop and future mobile clients do not embed II login. They open `https://dmsg.net/_/login` in the system browser, where II delegates directly to the client's session public key and the result returns to the client. The page has no login state, reads/saves no dmsg.net session and holds no usable private key.

## 1. Why dmsg.net hosts the page

dmsg.net is an II derivation origin (`derivationOrigin`); its code can already request a delegation for the user's Principal after II confirmation. Hosting login there adds no trust point or change to either site's `ii-alternative-origins`: `https://panda.fans/.well-known/ii-alternative-origins` already includes `https://dmsg.net`, allowing the same page to serve old Principals with `https://panda.fans` as derivation origin. The web bridge `connect.dmsg.net` never hosts login and is never listed in `ii-alternative-origins`.

The existing `/_/oauth/deeplink` continues serving old clients by reusing the site's own login state and appending a delegation; it is unchanged.

## 2. Flow

```mermaid
sequenceDiagram
  participant C as dmsg daemon
  participant B as System browser
  participant L as https://dmsg.net/_/login
  participant II as Internet Identity
  C->>C: Generate in-memory Ed25519 session key and state; listen on loopback
  C->>B: Open https://dmsg.net/_/login#<request>
  B->>L: Load page; read and immediately clear fragment
  L->>L: Validate; show local dMsg port and derivation origin
  L->>II: icrc34_delegation { publicKey: session_pubkey, maxTimeToLive, derivationOrigin }
  II-->>L: Delegation chain without target restriction
  L->>B: location.assign(next_url#<result>)
  B->>C: GET /auth/callback (fragment stays in browser)
  C-->>B: Minimal callback HTML
  B->>C: Read location.hash; same-origin POST /auth/callback
  C->>C: Check state, key and expiry; append restricted delegation; close listener
  C-->>B: Show that the page may be closed
```

Fragments are not sent in HTTP requests, so the daemon's `GET /auth/callback` cannot receive the result directly. Its minimal HTML reads `location.hash` and posts it to the daemon on the same origin. Chrome's Local Network Access restricts HTTPS-page `fetch` requests to loopback but not top-level navigation, so the login page returns the result using navigation (`location.assign`), not fetch or a form submission.

## 3. Request

The URL is `https://dmsg.net/_/login#<base64url(canonical CBOR request)>`, without a query. The request is:

```text
LoginRequest = {
  v: 1,
  state: bstr .size 32,            ; one-time random value generated by the daemon
  session_pubkey: bstr,            ; Ed25519 session public key in SPKI DER, 44 bytes only
  ttl_ms: uint,                    ; requested delegation lifetime in milliseconds
  derivation_origin: tstr,         ; "https://dmsg.net" or "https://panda.fans"
  next_url: tstr                   ; callback address; see section 5
}
```

The page checks canonical CBOR and canonical unpadded base64url with zero trailing bits; a closed key set; `v = 1`; nonzero `state`; Ed25519 SPKI DER with the fixed 12-byte prefix and 32-byte key; `ttl_ms` from 1 minute to 30 days (II's limit; the daemon requests 30 days); allowlisted `derivation_origin`; and `next_url` per section 5. Failure displays an error without contacting II or redirecting, since next_url itself may be invalid.

The page calls II's `icrc34_delegation` through `@icp-sdk/signer`, with `publicKey = session_pubkey`, `maxTimeToLive` from `ttl_ms`, and `derivationOrigin = derivation_origin`. It omits `targets`: II ignores them and returns an unrestricted chain, while the signer SDK treats requested targets followed by an unrestricted chain as an error. The page never generates or holds the session private key.

## 4. Callback

On success, navigate to `next_url#<base64url(canonical CBOR result)>`:

```text
LoginResult = {
  v: 1,
  state: bstr .size 32,
  delegation: bstr                 ; UTF-8 JSON from DelegationChain.toJSON(), @icp-sdk/core format
}
```

On failure:

```text
LoginError = { v: 1, state: bstr .size 32, error: tstr }
```

`error` is one of `user_cancelled`, `ii_error`, `derivation_origin_not_allowed` or `timeout`. Invalid request parameters cause no callback (section 3).

The daemon's `GET /auth/callback` serves the callback page, which sends `location.hash` unchanged via `POST /auth/callback` with `Content-Type: application/cbor` and decoded CBOR body. The daemon checks:

1. The listener exists only during login, for 10 minutes by default. It accepts a single POST and closes after success or failure; `GET /auth/callback` after closure returns 404.
2. `Origin` equals the loopback origin, `http://127.0.0.1:<port>` or `http://[::1]:<port>`. No CORS headers are emitted; other origins are rejected.
3. `state` matches the value generated for this login.
4. Parse `delegation` as DelegationChain: JSON bytes are hex, targets are hex Principal bytes and expiration is hex nanoseconds. The chain's first `publicKey` identifies the login Principal; the final delegation's `pubkey` must equal session public-key DER. Chain length is 1–8; each level's optional targets are preserved exactly as signed. Reject `permissions`, which II adds for query-only login. The earliest expiration must be after now and no later than `now + ttl_ms`.
5. Generate a fresh Ed25519 key and delegate to it using the session key. `targets` contains the registry/home-listed canisters and, when team wallets are enabled, the ICP ledger specified by the configured hub: 1–32 after deduplication. The login identity uses that ledger to pay activation fees; hub and wallet instances use the device's wallet key and are not login targets. IC intersects targets across the chain, restricting calls to that set. Discard the session private key when login ends, retaining only the new key and restricted chain. IC decides signature validity: the daemon performs read-only `my_account` queries on every home and discards the identity if any fail. A bound local workspace also requires the returned account to match its account.
6. After validation, retain the new key and restricted chain in memory and close the listener. If workspace fast unlock requires user presence (macOS Secure Enclave with Touch ID or login password), seal them under the local data key LDK after unlock. Locking clears only the memory copy; a later presence-verified fast unlock restores that login until expiry. Devices without presence verification do not persist it. Disabling fast unlock or resetting the workspace deletes the sealed login.

POST responses: 200 on success, 403 for wrong `Origin` or `Content-Type`, 400 for other validation failures, and 404 if no login is pending. The callback page sets `Content-Security-Policy: default-src 'none'; script-src 'unsafe-inline'; connect-src 'self'; frame-ancestors 'none'` and `Referrer-Policy: no-referrer`.

## 5. `next_url` allowlist

`next_url` accepts only:

- `http://127.0.0.1:<port>/auth/callback`
- `http://[::1]:<port>/auth/callback`

It also accepts exactly `https://dmsg.net/_/ios/auth/callback` for iOS. Explicit ports (including `:443`), trailing slashes, alternate casing, queries, fragments, other HTTPS addresses and custom schemes are refused. `localhost` remains forbidden. The message encoding and version remain 1.

iOS uses `ASWebAuthenticationSession.Callback.https(host:path:)`. The app's Associated Domains include `webcredentials:dmsg.net`, and dmsg.net's AASA must list the actual signed application. The production app is `net.dmsg.ios` of the LDC Labs Limited team (`S9Z2WAMAV8`): `src/dmsg_ios/project.yml` pins the team, and `src/dmsg_frontend/static/.well-known/apple-app-site-association` is generated by `scripts/ios/aasa.mjs S9Z2WAMAV8 net.dmsg.ios` and deployed with the frontend, served as a direct 200 JSON response without redirects. A team or bundle ID change updates both. Login is not operational until a frontend release with that file and the callback page is deployed. Outside the initiating system session the fallback page clears the fragment and asks the user to restart in the app, without forwarding or third-party scripts. A callback is consumed once; process termination invalidates pending requests.

## 6. Page requirements

- `/_/login` uses an independent layout without the site's login state, auth store or other business modules.
- Show only the destination, local dMsg with port number, the derivation origin and a Continue button. Contact II only after the click; provide no other actions.
- Immediately clear the fragment with `history.replaceState` after reading it, keeping it out of history.
- Write no cookies, localStorage or IndexedDB.
- Use the dmsg.net asset-canister header policy: `frame-ancestors 'none'`; `upgrade-insecure-requests` does not affect cross-host navigation to loopback; `form-action 'self'` means callbacks must use navigation, not form submission.

## 7. Security boundaries

- The page has no login state or usable key. Users authenticate with II; the page only forwards II's delegation to `session_pubkey` to the allowed next_url.
- II's session-key delegation is unrestricted. It coexists with the session private key only during callback validation, after which the daemon retains only the target-restricted chain (section 4, step 5).
- `next_url` is a closed set: loopback or the exact associated HTTPS path above. The system authentication session receives the HTTPS result; the fallback page neither stores nor forwards delegation. Delegation is useful only to this request's session private key. Clients still check state, key, expiry, derivation origin, canister targets and IC query results. This must not become a general remote redirect.
- A malicious process under the same OS user can listen on loopback and open the login page. The displayed local port cannot distinguish that process from dMsg. This is inherent to loopback callbacks (RFC 8252) and the OS-user boundary; local credentials follow the desktop design.
- Integrity of dmsg.net code is a trust prerequisite for II delegation regardless of where the login page is located.

## 8. Verification requirements

- Vectors: canonical CBOR/base64url for `LoginRequest`, `LoginResult` and `LoginError`, and rejected requests/callbacks, are generated and byte-compared by `dmsg_protocol` tests (`tests/vectors/client/login-v1.json`, rewritten with `DMSG_WRITE_CLIENT_VECTORS=1`). The page's `src/dmsg_frontend/src/lib/login/protocol.test.ts` uses the same file. Delegation signatures in these vectors are placeholders fixing encoding only.
- Page: missing parameters, non-closed key sets, out-of-range TTL, disallowed derivation origin, localhost and callbacks outside the closed set fail before II contact. Check fragment removal and success/failure callback fragments. Vitest covers protocol/flow modules in `src/dmsg_frontend/src/lib/login/`; rendering has separate browser checks. Real iOS II popups, passkeys, AASA and fragment delivery require device acceptance; protocol tests do not prove them.
- Daemon: reject wrong state/key, permissions, expired/overlong TTL and login-page errors; accept unrestricted chains and append the session-key-signed restricted level (`src/dmsg_client/src/login_tests.rs`). External-Origin POST returns 403 and closes listening; repeated POST and GET after closure return 404 in E2E tests.
- E2E: in Local, the test impersonates the login page and issues an unrestricted delegation from a generated Ed25519 login identity as II would. It submits through the daemon callback, and IC accepts the appended level (`tests/dmsg_integration/tests/desktop.rs`). The daemon has no test-only login path. Real II requires manual staging acceptance.
