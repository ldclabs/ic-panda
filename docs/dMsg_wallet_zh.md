## 1. 产品定义

**dMsg Wallet 是由链上策略和成员共同管理的多链团队钱包。**每个团队拥有一个 ICP canister，保存成员、策略、提案和审计记录。ICP/ICRC 资产由钱包直接调用账本支出；BTC、EVM、Solana 交易由钱包按已批准意图构造并通过 ICP 链密钥签名，再由成员客户端广播。

链密钥地址不要求团队备份助记词。账户设备、本机钱包身份及可选协签密钥仍有各自的保管与恢复责任；“无助记词”不代表没有密钥，也不代表不依赖 ICP、钱包代码和治理。

目标用户是团队运营资金的管理者：把多链收款、成员分工、多人批准、延时、协签和审计集中到同一流程。需要 SNS 提案管理的资金继续留在 SNS 国库。

## 3. 产品原则

1. **一团队一实例。**地址、成员、策略、审计和 cycles 独立保存；每个实例可接受升级或锁定代码。
2. **先批准意图，再执行。**设备批准绑定钱包、操作、策略版本和决定类型；客户端认证读取完整提案，外链计划另做独立解码。
3. **成员票数与设备协签分开。**同一账户在两台设备上仍是一个成员、最多一票；独立协签密钥可以另设 k-of-l 阈值。
4. **重试沿原记录恢复。**广播失败先重广播；结果未知的账本付款沿固定参数或真实区块对账，不能用再建一笔付款替代。
5. **已有资金不由订阅续费解锁。**运行中的钱包不检查创建者套餐，也没有按套餐关闭地址、协签、批准或提现的实现；仍受团队策略、cycles 和网络可用性约束。
6. **明确各层信任。**认证读取证明来源，独立解码核对交易，审计记录行为；这些都不是外链结算证明，也不能替代成员对完整内容的判断。

## 4. 成员、角色与身份

成员可以是 dMsg 账户或直接调用的 Principal。创建者为活跃 Admin；新增成员先处于 `Invited`，本人加入后才可行动。

| 角色 | 可提案 | 批准计数 | 否决 / 冻结 |
| --- | --- | --- | --- |
| Admin | 全部意图 | 管理类与支出/操作类 | 可以 |
| Approver | 全部意图 | 支出/操作类，不计管理阈值 | 可以 |
| Proposer | 全部意图 | 不计 | 不可以 |
| Viewer | 不可提案 | 不计 | 不可以 |
| Recovery | 仅成员新增、移除和更新 | 不计；自己发起的恢复提案无需批准，等待 7 天 | 不可以；等待期间 Admin/Approver 可否决其提案 |

账户成员每台设备使用一把本地加密保存的 Ed25519 钱包密钥，加入时经 `WalletJoin` 设备批准绑定其 Principal，每台设备一个，每成员最多 4 台设备。设备加入时可接管所列设备的绑定，登录恢复后可接管其余全部绑定；丢失的设备也可凭账户批准解绑，成员保持有效。登录身份负责在 user home 提交设备批准；钱包身份负责调用动态钱包实例。两者不是同一用途。

创建、加入、批准/拒绝/否决经审批中心，账户设备须具有 `WalletApprove` 能力；Principal 成员直接以 caller 身份决定。提案不自动附带提案人的批准，须另行投票。非 Viewer 成员可执行已经获准的操作，但执行入口不会授予新的批准权。

成员新增、移除、更新及首次加入都会推进授权版本，旧版未执行提案变为 `Stale`。活跃成员绑定、替换或解绑设备都不重复推进版本。账户设备撤销不等于钱包成员变更：被撤销设备的钱包绑定在解绑前仍然有效，钱包已记录的票数也不会仅因 home 的安全纪元变化而自动撤销，需结合冻结、解绑、成员变更等钱包操作处理。

## 5. 地址、协签与策略

### 5.1 地址与资产

默认地址编号在整个钱包内唯一：0 为 ICP、1 为 BTC P2TR、2 为 EVM、3 为 Solana；新地址从 4 起分配。每钱包最多 256 个地址。EVM 各链共用派生密钥和地址，由 chain ID 区分网络；ICP 地址对应钱包 Principal 下的子账户。

资产身份使用账本、EVM chain ID 与合约、Solana mint 等精确信息，不靠名称识别。转账支持 ICP、ICRC-1、BTC、EVM 原生币/ERC-20、SOL/SPL；可支出资产由策略控制。桌面使用精确整数换算，未知精度时明确按原子单位输入；显示 ICP AccountIdentifier 只增加收款表示，不改变账户模型。

### 5.2 三种控制方式

| 方式 | 执行要求 | 保护边界 |
| --- | --- | --- |
| CK 链钥 | 钱包按成员批准和策略执行；外链由 ICP 链密钥签名 | 依赖 ICP、钱包代码及未锁定时的 controller 治理 |
| CS 协签 | 在成员批准之外，钱包要求指定密钥对精确计划摘要满足协签阈值；ICP 类操作绑定提案摘要 | 由钱包代码强制；Admin 阈值 + 24 小时可调整或移除普通地址协签，不防恶意升级绕过 |
| NC 链上双控 | 当前仅 Bitcoin Taproot：L1 同时要求链密钥与 BIP-340 协签密钥 | L2 在 UTXO 达到设定区块年龄后允许链密钥单独花费；可选 L3 由恢复密钥在另一时间锁后花费；不能宣称所有路径永久 2-of-2 |

普通 CS 密钥生成目前支持 macOS 与 iOS 的 Secure Enclave P-256，以及本机 LDK 加密保存的软件 P-256。要求硬件而硬件不可用时直接失败，不静默降级：桌面随后询问是否改建软件密钥，CLI 只有加 `--software` 才建软件密钥，iOS 只建 Secure Enclave 密钥。canister 的 `hardware` 标记来自登记声明，没有硬件远程证明。硬件私钥不可导出也不等于有可信交易显示。

两端的差异：macOS Secure Enclave 每次在场确认最多签 32 个摘要，iOS 最多 64 个；关闭 iPhone 锁屏密码会使其 Secure Enclave 密钥失效，钱包需要另有协签人才能继续使用。

NC 协签密钥是 BIP-340 Taproot 密钥，Secure Enclave 不能直接持有，因此由“设备软钥匙”承担：每台设备有一个随机根，用一把或几把专用的 Secure Enclave 钥匙封存（保护者），创建时不弹窗，打开需要本人在场；没有这类硬件的设备只有在用户明确选择后才把根以软件形式保存在本机 LDK 下。每个钱包的钥匙由根派生，登记为 `Bip340`、`hardware: false` 的协签人，因此要求硬件协签人的钱包会拒绝它。签 L1 花费时客户端先用自己的解码器确认计划走 L1、叶子里是本机登记的公钥，再请本人打开根，对每个输入的脚本路径 sighash 直接签名（每次使用新的随机辅助数），派生出的公钥与登记的不符就拒签。含原生签名的协签包版本为 2，旧客户端会明确拒绝；只含普通签名的协签包仍是版本 1。

L1 叶子承诺的是某一台设备的钥匙，换设备时需要“迁移 NC 地址”：新设备登记自己的软钥匙（`AddCosigner`），新建链密钥延时与恢复钥匙都沿用旧地址的 Taproot 地址（`AddAddress`），资产档位要求地址簿时先加入地址簿并等待冷却，再以一笔无找零的转账把旧地址的 UTXO 扫到新地址：旧设备仍可签名时走 L1；否则走 L2，只花已满 `chain_key_after` 个区块的 UTXO，并显示每个 UTXO 最早可花费的区块高度，可以分批扫。每一步都是团队照常审批的提案；扫完后新设备在本机把旧地址标为“已归档”。

多设备协签必须针对同一计划。导入签名包只收集，不自动执行；每个协签人须覆盖全部待签摘要，重复导入不增加人数。导入和执行前，客户端按协签人当前的公钥重新校验已收集的签名；用已更换的钥匙做出的签名被搁置，并提示相应协签人重新签名。协签钥匙可以原地更换：所属成员用旧钥匙即时轮换；旧钥匙丢失时经 Admin 提案在 24 小时后替换，冻结时也可进行；用旧钥匙收集的签名须重新签。删除被普通地址策略引用的密钥或成员前，须先调整协签策略。Taproot 脚本承诺的密钥不会因移除所属成员而消失。

### 5.3 策略的实际含义

| 规则 | 行为 |
| --- | --- |
| 成员阈值 | 支出/操作类计 Admin 与 Approver；管理类只计 Admin，二者阈值独立 |
| 分档金额 | 按资产汇总：已达批准要求但尚未执行的有效预留 + 过去 24 小时开始执行/签名的金额 + 当前提案金额；提交与批准时计算，批准期间要求只提高不降低 |
| 预留 | 达到批准要求后持续保留，等待超过一天不会释放；取消、失效或确定无出金等结果才释放；签名失败且尚无已签交易时恢复预留 |
| 日额度 | 超过 `daily_limits` 时要求全部活跃批准人，并采用该资产各档的最长延时；不等于硬性限额 |
| 地址簿 | `book_only` 档只接受已过冷却期的收款条目；没有自动“地址簿降一档”规则 |
| 延时与否决 | 达阈值后开始延时；任何 Admin/Approver 可在延时中否决。被否决的提案终止，需要重新提案 |
| 冻结 | Admin/Approver 可直接冻结；只允许解冻和成员变更继续提案、批准与执行，批量/签名停在下一步之前；已签交易无法撤回 |
| 自动充值 | 已配置的 `refuel()` 是独立预授权运维入口，冻结不阻止它；受余额条件、单次 ICP 和每日次数限制 |
| 版本与期限 | 首次执行重新核对当前成员票数、授权版本、期限和冻结；Recovery 还须仍为活跃恢复成员 |
| 执行预算 | 每 UTC 日阈值签名数受 `daily_signatures` 限制，按摘要数量在签名前计数；它不是钱包全部 cycles 消耗的硬上限 |

`SetPolicy`、`RemoveMember`、`SetCosign`、`RemoveCosigner`、`ReplaceCosigner`、`AcceptUpgrade`、`LockCode`、`ReleaseEvmNonce` 走 Admin 阈值 + 24 小时；解冻延时取策略。新增地址、协签人、成员及更新成员走 Admin 阈值，无固定延时。Recovery 发起的成员变更统一等待 7 天。

## 6. 使用流程

### 6.1 创建与激活款

**当前桌面暂停新建。**[统一开关](../src/dmsg_desktop/src/shared/wallet-availability.ts) 同时控制按钮与主进程 RPC 边界，阻止创建、报价及报价预览。已有钱包、加入、历史激活继续处理、终止及退款可用；CLI、daemon 与 hub 的创建能力仍在，hub 另有治理暂停开关。

可用创建通道的流程为：检查设备批准资格和付款余额 → 获取 15 分钟报价 → 人工核对名称、成员、策略和激活费 → 先完成 user home 批准核验 → 向报价子账户付款 → hub 读余额并创建、安装钱包。hub 用自己的 cycles 池支付创建与初始余额，再从激活收入中回填该池。

已付款任务可继续原激活。尚未安装代码的 `Paid/Created` 任务可由报价调用者终止，删除空实例、释放配额后退款；已经安装代码的实例不走此退款路径。收入只归集固定报价，超额款、迟到款及可退的失败/过期款独立领取，扣账本手续费。客户端保留已付款报价以发现迟到款，无可显示余额时隐藏。

邀请成员本人确认加入。通知频道可绑定到已有频道，`channel_hint` 是初始提示，本机账户可覆盖；不会自动创建频道。

### 6.2 日常支出

1. 选择来源地址、精确资产、完整收款地址、金额和手续费上限；预览提供余额、费用及当前策略要求，不预留资金。
2. 成员通过独立审批窗口核对认证提案、当前钱包状态及决定。管理操作展示变更内容；未知或不完整意图不能批准。
3. 达到阈值并过延时后执行。ICP/ICRC 由钱包直接调用账本；外链先准备计划，客户端独立解码，必要时收集协签，再由钱包签名并由客户端广播。
4. 查看真实账本区块或外链交易记录。外链 `Settled/Failed` 是成员依据 RPC 提交的回报，钱包没有独立验证外链结算；界面、频道与审计不能把它升级为链上证明。

### 6.3 执行异常

| 情况 | 用户操作与边界 |
| --- | --- |
| 外链广播失败或等待确认 | 优先重广播原字节；BTC 只能同输入替换，EVM 只能同 nonce 替换，费用仍受原提案上限约束 |
| Solana 普通已签交易 | 不允许换 blockhash 重签，也不能靠等待固定秒数后重签；后来初始化持久 nonce 不改变旧提案规则 |
| Solana 需要可替换交易 | 在资产与地址区显式初始化持久 nonce；后续付款替换必须保持首签的 nonce 模式与值 |
| EVM 待处理 nonce | 详情可发起精确绑定原提案与 nonce 的取消或释放提案；释放不代表原交易已失效，取消回报也不抹掉原付款的已签事实与支出计数 |
| ICP/ICRC 结果未知 | 沿原参数重试；账本返回 `TooOld` 后仍保留未知作业。填写原账本的真实区块与批量序号，由钱包匹配完整转账后恢复，不能填“未付款”来授权新付款 |
| 批量部分成功 | 保留已成功区块，继续剩余项；从未发送的项首次即被账本以 TooOld 拒绝时明确失败，不撤销已完成转账 |

## 7. 桌面、智能体与通知

桌面分为概览、资产与地址、交易与提案、团队与安全四个主区；历史和审计从交易区进入，运行管理从团队与安全进入。支持分页、按编号定位、精确金额、收款二维码、协签包交换、周期刷新、资源状态与 RPC 诊断。切换账户或钱包后丢弃旧请求结果；网络与硬件等待不占住 daemon 的全局客户端锁。

MCP 工具为 `dmsg_wallet_list`、`dmsg_wallet_balances`、`dmsg_wallet_propose_transfer`、`dmsg_wallet_proposal_status`、`dmsg_wallet_execute`、`dmsg_wallet_report_broadcast`。能力分别由 `wallet.read`、`wallet.propose:<wallet>`、`wallet.execute:<wallet>` 控制；代提案还要求成员登记该 Agent ID。没有批准工具，协签需要人工时转入审批中心。

频道发送 `dmsg-wallet-event/1` 加密提示。接收方必须重新读取钱包，消息与 `dmsg://wallet/...` 链接只负责导航；通知失败不回滚已经完成的资金操作。审计导出注明范围、链头和验证时刻，不把单页冒充完整历史或外链对账证明。

## 8. 价格、套餐与运行成本

| 项目 | 已实现规则 | 尚属配置或建议 |
| --- | --- | --- |
| 创建配额 | hub 从 commerce 的 `refresh_entitlement` 获取套餐，按 `HubPricing.quotas` 限制创建数；未配置套餐为 0 | Plus 1 / Pro 3 / Max 10 是初版建议，代码不固定该表，也允许配置 Free 配额 |
| 激活费 | 固定 ICP e8s；初始 cycles、回填 hub 的 ICP 份额和收入账户由治理配置 | 约 10 USD 初值不是价格锚定或自动换汇机制 |
| 运行成本 | 各钱包支付自身 cycles；外链手续费由相应链资产支付，退款也扣账本费 | 不保证固定美元签名成本或固定年限续航，应按部署参数和实际消耗评估 |
| 高级功能 | 当前没有按 Pro/Max 限制 CS、NC 或批量转账的运行时检查 | 高级套餐分层、透明页自定义域名未落地 |

hub 只检查创建资格，套餐过期不会自动剥夺已有成员权限或禁止新增地址。创建费用回填 hub cycles 与新实例获得的初始 cycles 是两项配置，不应在界面或文案中混为同一笔即时兑换。

会员权益列表通过 `get_hub_config` 读取当前 `HubPricing.quotas`，同时显示设备和团队钱包额度。未配置的档位显示 0；读取失败显示未知并提示刷新，不用初版建议值替代实际配置。展示不绕过钱包开通时的服务端检查。

## 9. 种子钱包与治理

ICPanda DAO 团队钱包仍可作为种子用户，持有团队运营资金，使用成员阈值、地址簿、延时和可选协签；可另设离线保管的 Recovery 成员。hub 收入账户可经治理指向该钱包，其他业务收入须逐个核对其收款配置和归集调用权限后接入。

这不表示种子钱包已创建、收入已切换或公开透明页已上线。需要 SNS 治理的资金继续通过 SNS 国库处理，不能把团队钱包的成员批准等同于 SNS 投票。

## 10. 安全与恢复边界

| 边界 | 产品承诺的范围 |
| --- | --- |
| 升级与 controller | 当前 hub 代码要求实例先接受精确版本和哈希，并把升级、锁定串行化；但 hub 仍是未锁定实例的唯一 controller，其自身治理可改变代码，因此仍是信任根 |
| 代码锁定 | Admin 阈值 + 延时接受后，由 hub 在实例 Running 时清空 controllers。之后失去常规升级修复能力，不能消除已存在漏洞或保证永久运行 |
| CS 与恢复 | 普通协签可通过授权的管理员延时提案调整；它补充成员批准，不是独立于钱包治理的永久链上锁 |
| Taproot NC | L1 的双签由 Bitcoin 脚本约束，但 L2 到期允许链密钥单独支出；L3 可选且须恢复密钥持有人自行构造交易。相对时间锁按 UTXO 年龄计算 |
| cycles | 365 天 `freezing_threshold` 用于计算冻结储备，不是“耗尽后保证保留一年”；预授权充值仍需可用 ICP、CMC 与外部触发，不能替代余额维护 |
| 已签交易 | 冻结、成员撤销、取消界面状态或释放 nonce 都不能撤回已交付的有效签名 |
| 认证与外链 | 证书证明钱包返回的状态，审计哈希证明记录一致性；外链余额、费用、资产元数据和回报依赖所用节点，未实现 canister 链上核对 |
| 客户端与硬件 | 独立解码能拦下不匹配的计划，但仍须核对完整收款方与意图；硬件声明、设备在场与可信显示是不同能力 |
| 隐私 | `policy.public` 控制普通读取权限，不把 canister 内成员、金额、地址变成端到端加密秘密；链上交易本身仍可观察 |

成员全失联时，预先配置的 Recovery 可在 7 天窗口后修改成员；没有可用恢复路径时不能承诺找回资金。本产品没有法币、交易所、自动交易、通用 WalletConnect 或 ICP dapp signer 的完整实现。
